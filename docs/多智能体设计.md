## 多智能体系统设计文档

## 1. 概述

### 1.1 设计目标

本系统采用**协调器-工作器（Orchestrator-Worker）架构**，基于 LangGraph 的 Send API 实现多智能体协作，用于自动化旅行行程规划。核心目标包括：

- **任务分解与并行执行**：将复杂的旅行规划任务分解为多个子任务，由不同的工作节点并行处理
- **动态任务调度**：根据执行进度动态生成和分配任务
- **状态共享与聚合**：通过共享状态机制让多个工作节点并行写入结果
- **结果合成**：汇总所有工作节点的输出，生成完整的旅行计划

### 1.2 核心技术栈

- **LangGraph**：用于构建状态图和工作流
- **Send API**：实现动态节点创建和任务委派
- **MCP (Model Context Protocol)**：集成高德地图和酒店服务
- **LangChain**：提供 LLM 调用和工具管理能力

### 2.2 核心组件

#### 2.2.1 协调器（Orchestrator）

**职责**：
- 分析当前执行状态
- 生成待执行的行程部分（TripSection）
- 动态分配任务给工作节点
- 管理任务依赖关系

**状态**：
```python
class CoordinatorState(TypedDict):
    request_id: str                    # 请求ID
    request: Dict[str, Any]            # 原始请求
    destination: str                   # 目的地
    duration: int                      # 行程天数
    budget_level: str                  # 预算等级
    start_date: str                    # 开始日期
    preferences: List[str]             # 用户偏好
    hotel_preferences: List[str]       # 酒店偏好
    
    sections: List[TripSection]        # 行程计划（由 orchestrator 生成）
    completed_tasks: Annotated[List[Dict[str, Any]], add]  # 已完成任务（共享状态）
    raw_attractions: List[Dict[str, Any]]  # 原始景点数据
    raw_weather: List[Dict[str, Any]]      # 原始天气数据
    final_response: Optional[Dict[str, Any]]  # 最终响应
```

#### 2.2.2 工作节点（Workers）

系统包含三种类型的工作节点：

##### 景点搜索工作节点（AttractionSearchWorker）
- **输入**：目的地、用户偏好
- **输出**：景点列表（raw_attractions）
- **工具**：maps_text_search（高德地图文本搜索）

##### 天气查询工作节点（WeatherSearchWorker）
- **输入**：目的地
- **输出**：天气数据（raw_weather）
- **工具**：maps_weather（高德地图天气查询）

##### 每日规划工作节点（DailyPlanningWorker）
- **输入**：天数、目的地、分配的景点、天气数据、预算等级
- **输出**：每日行程计划（DailyPlan）
- **子任务**：景点规划、酒店规划、餐饮规划、预算计算

#### 2.2.3 合成器（Synthesizer）

**职责**：
- 汇总所有工作节点的结果
- 生成行程标题和每日主题
- 计算总预算
- 验证相邻天行程的合理性
- 组装最终的 TripPlanResponse

### 3.2 状态流转

#### 阶段 1：数据收集
1. **Orchestrator** 生成景点搜索和天气查询任务
2. **Workers** 并行执行，将结果写入 `completed_tasks`
3. **Orchestrator** 检测到阶段1完成，进入阶段2

#### 阶段 2：每日规划
1. **Orchestrator** 从共享状态读取 `raw_attractions` 和 `raw_weather`
2. **景点分配**：将景点均匀分配到每一天
3. **Orchestrator** 为每天生成一个 `daily_planning_worker` 任务
4. **Workers** 并行执行每日规划，将结果写入 `completed_tasks`

#### 阶段 3：结果合成
1. **Synthesizer** 从 `completed_tasks` 提取所有 DailyPlan
2. 生成标题和主题
3. 计算总预算并验证
4. 返回最终响应

## 4. 执行流程

### 4.1 完整执行流程

```
1. 初始化阶段
   ├─ OrchestratorWorkerPlanner.plan_trip() 被调用
   ├─ 初始化 CoordinatorState
   ├─ 计算行程天数
   └─ 调用 graph.ainvoke()

2. 第一次循环 - 阶段1
   ├─ START → orchestrator_node
   │   └─ 生成 2 个 TripSection（景点搜索 + 天气查询）
   ├─ assign_workers
   │   ├─ 创建 attraction_search_worker
   │   └─ 创建 weather_search_worker
   ├─ Workers 并行执行
   │   ├─ attraction_search_worker → 返回 raw_attractions
   │   └─ weather_search_worker → 返回 raw_weather
   └─ should_continue → 返回 "orchestrator"

3. 第二次循环 - 阶段2
   ├─ orchestrator_node
   │   ├─ 检测到阶段1完成
   │   ├─ 读取 raw_attractions 和 raw_weather
   │   ├─ 调用 _allocate_attractions_to_days() 分配景点
   │   └─ 生成 N 个 TripSection（N = duration）
   ├─ assign_workers
   │   └─ 创建 N 个 daily_planning_worker
   ├─ Workers 并行执行
   │   └─ 每个 daily_planning_worker → 返回一个 DailyPlan
   └─ should_continue → 返回 "synthesizer"

4. 最终阶段
   ├─ synthesizer_node
   │   ├─ 汇总所有 DailyPlan
   │   ├─ 生成标题和主题
   │   ├─ 计算总预算
   │   ├─ 验证相邻天
   │   └─ 组装 final_response
   ├─ synthesizer → END
   └─ 返回 TripPlanResponse
```

## 6. 关键机制

### 6.1 Send API 动态节点创建

**原理**：
- LangGraph 的 `Send` API 允许在运行时动态创建节点
- 每次调用 `Send` 都会创建一个新的工作节点实例
- 工作节点可以并行执行

**实现**：
```python
def assign_workers(state: CoordinatorState) -> List[Send]:
    sections = state.get("sections", [])
    sends = []
    for section in sections:
        if section.task_type == "daily_planning":
            sends.append(Send(
                "daily_planning_worker",
                {
                    "task_input": section.task_input,
                    "completed_tasks": []
                }
            ))
    return sends
```

### 6.2 状态共享与聚合

**原理**：
- 使用 `operator.add` 作为 reducer
- 所有工作节点的输出会自动合并到 `completed_tasks` 列表中
- 每个工作节点只写入自己的结果，不会覆盖其他节点的结果

**实现**：
```python
class CoordinatorState(TypedDict):
    completed_tasks: Annotated[List[Dict[str, Any]], add]  # 自动聚合
```

**效果**：
```python
# Worker 1 返回
{"completed_tasks": [{"task_type": "attraction_search", "result": [...]}]}

# Worker 2 返回
{"completed_tasks": [{"task_type": "weather_search", "result": [...]}]}

# 聚合后的状态
{
    "completed_tasks": [
        {"task_type": "attraction_search", "result": [...]},
        {"task_type": "weather_search", "result": [...]}
    ]
}
```

### 6.3 任务依赖管理

**实现**：
```python
def should_continue(state: CoordinatorState) -> Literal["synthesizer", "orchestrator"]:
    completed_tasks = state.get("completed_tasks", [])
    duration = state.get("duration", 1)
    
    phase1_completed = sum(1 for t in completed_tasks 
                          if t.get("task_type") in ["attraction_search", "weather_search"])
    phase2_completed = sum(1 for t in completed_tasks 
                          if t.get("task_type") == "daily_planning")
    
    if phase2_completed >= duration:
        return "synthesizer"
    return "orchestrator"
```

**逻辑**：
- 阶段1：景点搜索 + 天气查询必须完成
- 阶段2：所有天数的每日规划必须完成
- 只有阶段2完成后才进入合成器

### 6.4 景点分配算法

**目标**：将景点均匀分配到每一天

**实现**：
```python
def _allocate_attractions_to_days(attractions: List[Dict[str, Any]], duration: int) -> Dict[int, List[Dict[str, Any]]]:
    if not attractions:
        return {}
    
    total_attractions = len(attractions)
    attractions_per_day = max(2, min(4, total_attractions // duration))
    
    shuffled_attractions = attractions.copy()
    random.shuffle(shuffled_attractions)
    
    day_attraction_mapping = {}
    for day_num in range(1, duration + 1):
        start_idx = (day_num - 1) * attractions_per_day
        end_idx = start_idx + attractions_per_day
        
        day_attraction_mapping[day_num] = shuffled_attractions[start_idx:end_idx]
    
    return day_attraction_mapping
```

**策略**：
- 每天分配 2-4 个景点
- 先打乱景点顺序，避免重复
- 均匀分配到每一天

## 7. 并发控制

### 7.1 并发执行

**景点搜索和天气查询**：
- 完全并行，无依赖
- 同时执行，节省时间

**每日规划**：
- 多个 `daily_planning_worker` 并行执行
- 每个节点独立规划一天
- 使用相同的景点和天气数据

### 7.2 状态隔离

**问题**：多个工作节点共享同一个 LLM 实例可能导致并发风险

**当前实现**：
- 每个工作节点独立调用 `invoke_llm_with_system`
- 状态通过 `completed_tasks` 共享，但写入是原子操作
- 使用 `operator.add` reducer 保证数据一致性

**潜在风险**：
- 如果使用共享的 LLM 实例，可能出现状态污染
- 建议每个工作节点使用独立的 LLM 实例

## 9. 性能优化

### 9.1 并行执行优势

**串行 vs 并行**：
- 串行：O(n) 天数 * 每天执行时间
- 并行：O(1) 天数 * 每天执行时间

**示例**：
- 7天行程，每天规划耗时 10 秒
- 串行：70 秒
- 并行：10 秒（理想情况）

### 9.2 工具调用优化

**减少工具调用次数**：
- 景点搜索：一次性搜索所有景点，然后分配
- 天气查询：一次性查询所有天气，然后按天过滤

**LLM 调用优化**：
- 每个工作节点独立调用 LLM，避免串行等待
- 使用 `max_tool_iterations` 限制工具调用次数

## 11. 已知问题与改进方案

### 11.1 并发风险

**问题**：多个工作节点共享同一个 LLM 实例可能导致状态污染

**改进方案**：
- 每个工作节点使用独立的 LLM 实例
- 或者使用 LLM 的会话隔离机制

### 11.2 工具连接竞争

**问题**：ToolRegistry 共享可能导致 MCP 连接竞争

**改进方案**：
- 每个 Worker 创建独立的 ToolManager 实例
- 或者使用连接池管理 MCP 连接

### 11.3 状态隔离问题

**问题**：多个 Agent 并行执行时可能出现状态隔离问题

**改进方案**：
- 为每个工作节点创建独立的状态副本
- 使用更细粒度的状态管理

## 12. 总结

### 12.1 核心优势

1. **高效并行**：充分利用多核 CPU，大幅缩短执行时间
2. **动态调度**：根据执行进度动态生成任务，提高灵活性
3. **模块化设计**：每个工作节点独立，易于维护和扩展
4. **状态共享**：通过 reducer 机制实现安全的状态共享

### 12.2 适用场景

- 需要并行执行多个独立任务的场景
- 任务之间存在依赖关系的场景
- 需要动态生成任务的场景
- 需要汇总多个子任务结果的场景

### 12.3 技术亮点

1. **Send API**：LangGraph 的动态节点创建能力
2. **Reducer 模式**：`operator.add` 实现自动状态聚合
3. **条件边**：灵活的任务流程控制
4. **MCP 集成**：无缝集成外部工具服务

## 智能旅行规划系统（AI Travel Planner）

### 项目简介

智能旅行规划系统是一个基于 **LangGraph 多智能体协作架构** 的全栈 AI 旅行规划应用。用户只需输入目的地、出行日期和个人偏好，系统即可自动生成包含景点、酒店、餐饮、天气、预算的完整行程方案。

项目采用前后端分离架构，后端基于 **FastAPI + LangGraph + 通义千问 LLM + 高德地图 MCP**，前端基于 **Vue 3 + TypeScript + 高德地图 JS API**。核心创新在于使用 LangGraph 状态图编排 **6 个专业化 Agent 节点**，通过三阶段流水线（记忆加载 → 并行搜索 → 按天循环规划 → 验证拼装 → 记忆存储）协作完成行程规划。系统具备三层记忆架构、MCP 结果缓存、地理验证、熔断降级等企业级能力，支持 30+ 热门旅游城市。

**技术栈：** FastAPI / LangGraph / LangChain / Vue 3 / TypeScript / 通义千问 LLM / 高德地图 MCP / Redis / Milvus 向量数据库 / Sentence-Transformers / Pydantic v2 / JWT

---

### 项目亮点

#### 1. 基于 LangGraph 的多智能体状态图架构

**难点：** 行程规划是一个复杂的端到端任务，涉及景点搜索、天气查询、按天分配景点、酒店推荐、餐饮规划、主题生成等多个子任务。若使用单一 Agent 处理，Prompt 过长导致上下文窗口溢出，输出质量不可控；且各子任务间存在复杂的数据依赖关系（如酒店推荐依赖当天景点位置，餐饮推荐依赖景点区域），单一 Agent 难以处理这种多层级依赖。

**方案：** 使用 LangGraph 状态图编排 6 个专业化 Agent 节点（记忆加载、并行搜索、按天规划、主题生成、响应拼装、记忆存储），每个节点聚焦单一职责，通过 `TripPlanState`（TypedDict）全局状态实现节点间的数据流转。图结构为：

```
START → load_memory → search_parallel → plan_daily (条件边循环) → generate_theme → assemble_response → save_memory → END
```

- **条件边循环**：`plan_daily` 节点通过 `add_conditional_edges` 实现按天循环，`current_day` 作为循环变量，当 `current_day > duration` 时跳转到 `generate_theme`。
- **状态驱动**：所有节点通过返回 dict 增量更新全局状态，已分配列表使用深拷贝更新避免引用污染。
- **依赖编排**：每天内部景点规划先行（酒店和餐饮依赖景点位置），酒店和餐饮 Agent 通过 ReAct 模式动态调用 MCP 工具搜索真实数据。

---

#### 2. 精细化 Prompt 工程与预算注入

**难点：** LLM 对模糊的预算描述（如"中等预算"）理解不一致，导致推荐的酒店价格波动大；多天规划时 LLM 容易重复推荐相同景点和餐厅；LLM 有时不遵守输出格式约束，返回非 JSON 文本。

**方案：** 每个 Agent 节点都有独立的 System Prompt 和动态 User Prompt，采用 **"角色定义 + 输出格式约束 + 业务规则 + 记忆注入"** 的四层 Prompt 结构：

- **预算量化注入**：引用 `BUDGET_RANGES` 常量，将具体金额上限（如"酒店不超过 600 元/晚"、"单餐不超过 100 元"）直接写入 Prompt，而非模糊的"中等预算"。
- **程序化去重**：`filter_unassigned_attractions` 在构建 Prompt 前移除已分配景点，`assigned_dining_names` 列表注入餐饮 Prompt 避免重复推荐，从源头消除重复。
- **记忆融合**：所有 `build_xxx_prompt` 函数都支持 `memory_context` 参数，将用户历史偏好（如"偏好历史文化类景点"、"上次去过故宫"）以自然语言追加到 Prompt 末尾。
- **格式强约束**：System Prompt 中反复强调"只输出合法 JSON"、"严禁输出任何非 JSON 内容"，配合多层解析容错兜底。

---

#### 3. 工具调用无限循环的三层防护

**难点：** 酒店和餐饮 Agent 采用 ReAct 模式通过高德地图 MCP 调用真实 API。但 LLM 可能陷入"无限工具调用"循环——不断调用搜索工具但始终不输出最终结果，导致 Token 消耗暴增、请求超时。同时 LLM 也可能跳过工具调用直接编造数据。

**方案：** 在 `_invoke_llm_with_tools` 中实现了三层递进式防护：

1. **首轮强制调用工具**：`tool_choice="any"` 确保首轮必须调用工具获取真实数据，避免 LLM 编造信息。若首轮仍未调用，追加警告消息强制重试。
2. **工具调用次数阈值 + 停止提醒**：当工具调用次数 ≥ 2 时，自动注入引导消息"你已经搜索到了足够的数据，请立即输出最终结果"，通过 Prompt 层面引导 LLM 收敛。
3. **硬性迭代上限**：`max_iterations=8` 作为最终兜底，达到上限后强制取最后一条 AI 消息返回。

三层防护从"软引导"到"硬限制"逐步升级，同时工具加载失败时自动降级为纯 LLM 调用，保证流程不中断。

---

#### 4. 三层记忆架构（短期 + 长期偏好 + 长期情景）

**难点：** 系统需要实现"越用越智能"的个性化推荐——记住用户去过哪些城市和景点、偏好什么类型的旅行、历史预算水平等。但记忆数据分布在不同存储介质中，且记忆读写失败不应阻断主流程。

**方案：** 实现了完整的三层记忆体系：

| 记忆层 | 存储介质 | 生命周期 | 用途 |
|--------|---------|---------|------|
| **短期记忆** | LangGraph State | 单次请求 | 当前行程的中间状态（已分配景点、天气数据等） |
| **长期偏好画像** | Redis Hash | 永久 | 偏好频次、去过的城市/景点、平均预算（滑动平均） |
| **长期情景记忆** | Milvus 向量库 | 永久 | 历史行程的自然语言摘要，支持语义检索 |

- **偏好画像**：Key 格式 `user_profile:{user_id}`，每次行程后增量更新，`build_memory_context` 将结构化数据转为自然语言注入 Prompt。已去过的景点通过程序化过滤从候选列表中移除。
- **情景记忆**：使用 `sentence-transformers/all-MiniLM-L6-v2` 生成 384 维向量，IVF_FLAT 索引 + COSINE 相似度，检索时通过 `filter` 参数实现用户隔离。行程摘要使用自然语言格式提升语义匹配质量。
- **延迟初始化**：Embedding 模型和 Milvus 连接延迟到首次使用时初始化，避免启动阻塞。HuggingFace 镜像通过 patch `huggingface_hub.constants` 解决模块级常量缓存问题。
- **优雅降级**：记忆加载/存储失败时仅记录日志，返回空上下文，不影响行程规划主流程。

---

#### 5. MCP 调用结果的 Redis 缓存层

**难点：** MCP 外部 API 调用（景点搜索、天气查询、酒店搜索等）是系统中最耗时的操作，同一城市的多次规划请求会产生大量重复调用。但不同类型数据的时效性差异大（天气变化快、景点详情基本不变），需要差异化缓存策略。

**方案：** 在 `ToolsManager.call_tool()` 中注入透明缓存层，对所有 MCP 调用自动拦截：

- **缓存 Key**：`mcp_cache:{tool_name}:{MD5(参数JSON)}`，参数序列化使用 `sort_keys=True` 确保参数顺序无关。
- **差异化 TTL**：天气 1 小时、景点搜索 24 小时、景点详情 72 小时、酒店/餐厅搜索 24 小时。
- **通用性保证**：缓存的是 parser 之前的原始数据，缓存命中后重新执行 parser，保证缓存数据可被不同调用方复用。
- **透明降级**：缓存读写失败仅记录警告，自动回退到实际 MCP 调用，对业务代码完全透明。

---

#### 6. LLM 输出的三层容错解析

**难点：** LLM 经常输出不合规的 JSON：附加 Markdown 代码块标记、字段类型不一致（字符串 vs 数字）、嵌套对象格式不一致。这些不一致会导致 Pydantic 校验失败，整个行程规划中断。

**方案：** 实现了三层容错链：

1. **JSON 提取层**（`parse_json_response`）：自动剥离 Markdown 代码块标记，兼容 ` ```json ``` ` 和 ` ``` ``` ` 两种包裹格式。
2. **字段级类型转换层**（`converters.py`）：`dict_to_attraction`、`dict_to_hotel`、`dict_to_meal` 对每个字段独立 try-catch，`visit_duration` 字符串→int 失败默认 120 分钟，`rating` 失败允许为 None，`location` 检查是否为 dict 再转换。
3. **节点级降级层**（`node_plan_daily`）：景点/酒店/餐饮三个规划阶段独立 try-catch，某阶段解析失败不影响其他阶段，使用空列表兜底。

---

#### 7. 多维度预算控制体系

**难点：** 纯 Prompt 约束无法保证 LLM 严格遵守预算上限，纯程序化计算又无法影响 LLM 的推荐选择。交通费用难以估算，固定值不准确。

**方案：** 实现了 Prompt-程序双轨约束：

- **Prompt 层**（引导）：将具体金额上限写入 Prompt，引导 LLM 在推荐时考虑价格因素。
- **程序层**（兜底）：`calculate_daily_budget` 基于 LLM 输出的结构化数据累加各项费用，`check_budget_compliance` 检查是否超标并分级告警（超标 vs 严重超标 1.5 倍阈值）。
- **动态交通估算**：基于景点间实际距离（Haversine 公式）× 每公里单价计算，设置最低保底值避免估算过低。
- **总预算汇总**：在 `node_assemble_response` 中汇总所有天的预算，超标时设置 `is_over_budget` 标志返回给前端展示。

---

#### 8. 企业级中间件与弹性设计

**难点：** 系统依赖多个外部服务（通义千问 LLM API、高德地图 MCP），单次行程规划耗时 30-60 秒，期间涉及多次 LLM 调用和 MCP 工具调用，任何环节失败都可能导致整个请求失败。同时需要防止恶意请求和高并发冲击。

**方案：** 实现了完整的中间件链和弹性设计：

- **滑动窗口限流**：双维度限流（全局 + 每 IP），记录请求时间戳清理 1 秒前旧请求，优先从 `X-Forwarded-For` 获取真实 IP，健康检查端点跳过限流。
- **熔断器**：`CircuitBreaker` 基于失败计数实现熔断（连续失败 N 次触发），超时后自动恢复（closed → open → closed 状态机），线程安全，`CircuitBreakerManager` 支持多服务独立熔断。
- **降级策略**：`@fallback_response` 装饰器在函数失败时返回预定义默认值；`@circuit_breaker_with_fallback` 组合装饰器将熔断器与降级策略结合，熔断后自动返回降级响应。
- **全链路追踪**：`RequestIDMiddleware` 为每个请求生成唯一 UUID，通过 `contextvars` 贯穿日志和 Agent 上下文。
- **双轨认证**：JWT 令牌认证（注册用户）+ Cookie 访客模式，无需登录即可使用核心功能。
- **统一异常处理**：按模块分段的错误码体系（1000-5999），全局异常处理器统一返回标准 JSON 响应。

---

#### 9. 地理位置验证与日期校验

**难点：** LLM 存在"幻觉"问题——推荐不在目标城市的景点、同一天景点距离过远。同时天气 API 仅支持未来 4 天预报，需要限制用户请求的日期范围。

**方案：**

- **地理验证**：内置 30+ 城市经纬度边界数据（`CITY_BOUNDS`），对所有 POI 验证是否在目标城市范围内，不合格自动移除。使用 Haversine 公式验证同一天景点间距离 ≤ 50km、相邻天首尾景点 ≤ 100km。景点无位置信息直接移除，餐饮/酒店无位置信息则保留。
- **日期校验**：在 Pydantic 模型层使用 `@model_validator` 实现，`start_date` 必须大于今天且不超过未来 4 天，`end_date` 不能早于 `start_date`，所有使用 `TripPlanRequest` 的路由自动生效。

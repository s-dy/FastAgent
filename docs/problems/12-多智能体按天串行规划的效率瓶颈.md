# 问题：Phase2 按天串行规划导致长行程耗时线性增长

## 问题描述

Phase2 的按天规划采用 **天与天之间串行、天内部并行** 的执行策略。虽然每天内部的景点、酒店、餐饮三个 Agent 是并行执行的，但天与天之间是严格串行的（第 1 天完成后才开始第 2 天）。这导致行程天数越多，总耗时线性增长。

## 代码层面的根因

`planner.py` 第 740-800 行，Phase2 使用 `for` 循环逐天规划：

```python
for day_num in range(1, duration + 1):
    logger.info(f"📅 正在规划第 {day_num}/{duration} 天...")
    
    day_result = self._plan_single_day(
        day_num=day_num,
        request=request,
        ...
        assigned_attraction_names=assigned_attraction_names,  # 依赖前几天的结果
        assigned_dining_names=assigned_dining_names,          # 依赖前几天的结果
    )
    
    # 更新已分配列表（下一天依赖这个数据）
    for attraction in daily_plan.attractions:
        assigned_attraction_names.append(attraction.name)
    for meal in daily_plan.dining:
        assigned_dining_names.append(meal.name)
```

**串行的原因**：每天的规划需要知道"前几天已经分配了哪些景点和餐厅"（`assigned_attraction_names` 和 `assigned_dining_names`），以避免重复推荐。这个数据依赖关系使得天与天之间无法并行。

## 影响范围

- 3 天行程：Phase2 耗时约 30-45 秒（每天 10-15 秒）
- 5 天行程：Phase2 耗时约 50-75 秒
- 7 天行程：Phase2 耗时约 70-105 秒
- 总体规划时间（含 Phase1 和 Phase3）可能超过 2 分钟，用户体验差

## 解决方案

### 方案一：两阶段并行策略

将 Phase2 拆分为两个子阶段：

**Phase2a**：所有天的景点规划并行执行，但在 Prompt 中传入所有候选景点和天数信息，让 LLM 自行分配避免重复。

```python
# 一次性让 LLM 为所有天分配景点
all_days_attraction_prompt = f"""
请为{destination}的{duration}天行程分配景点。
候选景点：{raw_attractions}
要求：每天 2-4 个景点，不同天不要重复，同一天景点距离不超过 50km。
输出格式：{{"day_1": [...], "day_2": [...], ...}}
"""
```

**Phase2b**：基于 Phase2a 的结果，所有天的酒店和餐饮并行规划。

### 方案二：乐观并行 + 冲突检测

所有天并行规划，但在 Prompt 中明确告知 LLM 这是第几天，并在 Phase3 中检测跨天重复：

```python
# 所有天并行执行
with ThreadPoolExecutor(max_workers=duration) as executor:
    futures = {}
    for day_num in range(1, duration + 1):
        futures[day_num] = executor.submit(
            self._plan_single_day,
            day_num=day_num,
            assigned_attraction_names=[],  # 不传已分配列表
            ...
        )

# Phase3 中检测并解决跨天重复
all_plans = [f.result() for f in futures.values()]
deduplicated_plans = self._resolve_cross_day_conflicts(all_plans)
```

### 方案三：流式输出 + 渐进式展示

保持串行规划，但通过 SSE 将每天的规划结果实时推送给前端，让用户看到渐进式的规划过程：

```
Phase2 开始 → 推送"正在规划第 1 天..."
第 1 天完成 → 推送第 1 天的完整数据，前端立即渲染
第 2 天完成 → 推送第 2 天的完整数据，前端追加渲染
...
```

用户感知到的等待时间从"全部完成才能看到"变为"第一天完成就能看到"，体验大幅提升。

## 推荐方案

**方案三（流式输出）** 是投入产出比最高的方案：
- 不改变现有的串行逻辑，避免引入跨天重复等新问题
- 用户感知的等待时间从 60s+ 降低到 10-15s（第一天完成的时间）
- 实现复杂度较低，只需增加 SSE 推送机制

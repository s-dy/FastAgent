# 项目亮点与难点

## 一、项目亮点

### 1. 基于 LangGraph 的协调器-工作器架构

本项目采用 **协调器-工作器（Orchestrator-Worker）架构**，基于 LangGraph 的 Send API 实现动态任务调度。系统包含协调器（Orchestrator）、多个工作节点（Workers）和合成器（Synthesizer），通过动态创建节点和状态共享机制实现高效的多智能体协作。

**为什么这样设计：**
- **动态任务调度**：Orchestrator 根据执行进度动态生成和分配任务，而非固定的流水线
- **高效并行执行**：所有工作节点并行运行，大幅提升执行效率（N 天行程从 O(n) 降至 O(1)）
- **状态共享与聚合**：通过 `operator.add` reducer 自动合并工作节点结果，避免复杂的状态管理
- **任务依赖管理**：通过条件边自动管理任务间的依赖关系，代码结构清晰

**图结构：**
```
START → orchestrator → [Send] → workers → should_continue → orchestrator/synthesizer
```

**执行流程：**
- **阶段1**：Orchestrator 生成景点搜索和天气查询任务，Send API 创建 2 个 Worker 并行执行
- **阶段2**：Orchestrator 检测到阶段1完成，将景点均匀分配到每一天，Send API 创建 N 个 DailyPlanningWorker 并行执行（N=天数）
- **阶段3**：Synthesizer 汇总所有工作节点结果，生成标题主题、计算总预算、验证相邻天行程

**核心代码体现：**
- `backend/app/agents/multi_agnet.py`：协调器-工作器架构实现，包含 Orchestrator、Workers、Synthesizer
- `backend/app/agents/utils/llm.py`：ReAct 模式的 LLM 工具调用引擎
- `backend/app/agents/utils/tools_manager.py`：MCP 工具统一管理（单例模式）

详细设计文档见：[`多智能体设计.md`](./多智能体设计.md)

### 2. 精细化 Prompt 工程设计

每个工作节点都有独立的 System Prompt 和动态 User Prompt，采用 **"角色定义 + 输出格式约束 + 业务规则 + 记忆注入"** 的四层 Prompt 结构：

| 组件 | System Prompt 核心约束 | 动态注入内容 |
|-------|----------------------|-------------|
| **景点规划 Worker** | 只输出合法 JSON 数组，2~4 个景点/天，景点同城且距离 ≤ 50km | 候选景点列表、天气、预算上限、用户偏好 |
| **酒店规划** | 必须先调用工具搜索，严禁编造酒店信息，输出单个 JSON 对象 | 当天景点位置摘要、预算等级、酒店偏好 |
| **餐饮规划** | 每天至少早午晚三餐，不重复推荐，自行估算价格 | 当天景点位置、已分配餐厅列表、预算上限 |
| **主题生成** | 标题吸引人，主题简洁（10 字内） | 每天景点摘要列表 |

**亮点：**
- 预算控制直接写入 Prompt：引用 `BUDGET_RANGES` 常量，将具体的金额上限（如"酒店不超过 600 元"）注入 Prompt，而非模糊的"中等预算"
- 记忆融合：所有 `build_xxx_prompt` 函数都支持 `memory_context` 参数，将用户历史偏好以自然语言追加到 Prompt 末尾
- 程序化过滤：`filter_unassigned_attractions` 在构建 Prompt 前移除已分配景点，从源头避免重复推荐

### 3. 工具调用无限循环的三层防护机制

ReAct 模式下 LLM 可能陷入"无限工具调用"——不断调用搜索工具但始终不输出最终结果。系统在 `_invoke_llm_with_tools` 中实现了三层防护：

**第一层：tool_choice 策略切换**
```python
# 首轮强制调用工具（确保获取真实数据）
llm_forced_tool = llm.bind_tools(tools, tool_choice="any")
# 后续轮次自动模式（LLM 自行决定是否继续调用）
llm_auto_tool = llm.bind_tools(tools)
```

**第二层：工具调用次数阈值 + 强制停止提醒**
```python
if tool_call_count >= 2:
    messages.append(HumanMessage(
        content="你已经搜索到了足够的酒店/餐厅数据。请不要再调用任何工具，"
                "立即从已有的搜索结果中挑选最合适的一个，按照要求的 JSON 格式输出最终结果。"
    ))
```

**第三层：硬性迭代上限**
```python
max_iterations: int = 8  # 达到上限后强制取最后一条 AI 消息返回
```

**额外保护：首轮未调用工具的重试机制**
```python
if tool_call_count == 0 and iteration == 0:
    messages.append(HumanMessage(
        content="你没有调用任何工具！请立即使用可用的工具来完成任务，不要直接回答。"
    ))
```

### 4. 三层记忆架构（短期 + 长期偏好 + 长期情景）

系统实现了完整的三层记忆体系，让 Agent 能够"记住"用户的历史偏好：

| 记忆层 | 存储介质 | 生命周期 | 用途 |
|--------|---------|---------|------|
| **短期记忆** | LangGraph State | 单次请求 | 当前行程的中间状态（已分配景点、天气数据等） |
| **长期偏好画像** | Redis Hash | 永久 | 用户偏好频次、去过的城市/景点、平均预算等结构化数据 |
| **长期情景记忆** | Milvus 向量库 | 永久 | 历史行程的自然语言摘要，支持语义检索 |

**偏好画像（Redis Hash）：**
- Key 格式：`user_profile:{user_id}`
- 存储字段：`trip_count`、`preferred_categories`（偏好频次）、`visited_cities`、`visited_attractions`、`avg_daily_budget`（滑动平均）
- 每次行程后增量更新，`build_memory_context` 将结构化数据转为自然语言注入 Prompt

**情景记忆（Milvus）：**
- 使用 `sentence-transformers/all-MiniLM-L6-v2` 生成 384 维向量
- IVF_FLAT 索引 + COSINE 相似度，检索时通过 `filter` 参数实现用户隔离
- 行程摘要使用自然语言格式（而非 JSON），提升语义检索的匹配质量

**记忆加载流程（`node_load_memory`）：**
1. 从 Redis 读取用户偏好画像 → 程序化过滤已去过的景点
2. 从 Milvus 检索相关情景记忆（最多 3 条）
3. 合并为 `memory_context` 文本 → 注入到各 Agent 的 Prompt 中

### 5. MCP 调用结果的 Redis 缓存层

MCP 外部 API 调用（高德地图景点搜索、天气查询、酒店搜索等）是系统中最耗时的操作。通过在 `ToolsManager.call_tool()` 中注入透明缓存层，实现了对所有 MCP 调用的自动缓存：

**缓存 Key 策略：**
```
mcp_cache:{tool_name}:{MD5(参数JSON)}
```
参数 JSON 序列化时使用 `sort_keys=True`，确保相同参数生成相同哈希。

**差异化 TTL：**

| 工具 | 场景 | 过期时间 |
|------|------|---------|
| `maps_weather` | 天气查询 | 1 小时 |
| `maps_text_search` | 景点搜索 | 24 小时 |
| `maps_search_detail` | 景点详情 | 72 小时 |
| `maps_around_search` | 酒店/餐厅搜索 | 24 小时 |

**透明拦截：** 缓存逻辑在 `ToolsManager.call_tool()` 内部实现，对业务代码完全透明。缓存的是 parser 之前的原始数据，保证缓存的通用性。缓存读写失败时仅记录警告，不影响主流程。

### 6. 企业级中间件链

后端实现了完整的中间件链，体现了生产级的工程实践：

**滑动窗口限流（`rate_limit.py`）：**
- 双重限流：全局限流 + 每 IP 限流
- 滑动窗口算法：记录请求时间戳，清理 1 秒前的旧请求
- 优先从 `X-Forwarded-For` 获取真实 IP，健康检查端点跳过限流

**熔断器（`circuit_breaker.py`）：**
- 计数阈值：失败次数达到 `failure_threshold` 后自动熔断
- 自动恢复：超过 `timeout` 时间后尝试恢复（closed → open → closed 状态机）
- 线程安全：使用 `Lock` 保护状态变更
- `CircuitBreakerManager` 支持多服务独立熔断

**降级策略（`degradation.py`）：**
- `@fallback_response` 装饰器：函数调用失败时返回预定义的默认值
- `@circuit_breaker_with_fallback`：熔断器 + 降级的组合装饰器，熔断后自动返回降级响应

---

### 7. 多维度预算控制体系

预算控制贯穿 Prompt 约束和程序化计算两个层面：

**Prompt 层面：** 将具体金额上限注入 Prompt（如"酒店预算不超过 600 元/晚"），从源头引导 LLM 输出合理价格。

**程序化计算（`budget.py`）：**
```python
BUDGET_RANGES = {
    "经济": {"hotel_max": 300, "dining_meal_max": 50, "daily_total_max": 500},
    "中等": {"hotel_max": 600, "dining_meal_max": 100, "daily_total_max": 1000},
    "豪华": {"hotel_max": 1500, "dining_meal_max": 300, "daily_total_max": 2500},
}
```
- 交通费用基于景点间实际距离动态估算（Haversine 公式 × 每公里单价），而非固定值
- 分级告警：区分"超标"和"严重超标"（1.5 倍阈值），日志中明确标注
- 总预算在 `node_assemble_response` 中汇总计算，超标时设置 `is_over_budget` 标志

---

### 8. 地理位置验证体系

系统内置了 30+ 城市的经纬度边界数据（`CITY_BOUNDS`），对 LLM 生成的所有 POI 进行程序化验证，有效解决 LLM "幻觉"问题：

- **城市边界验证**：使用经纬度矩形边界盒，验证每个景点/餐饮/酒店是否在目标城市范围内，不合格的自动移除
- **单日距离验证**：同一天相邻景点间距离超过 50km 时告警（Haversine 公式）
- **跨天距离验证**：相邻天首尾景点间距离超过 100km 时告警
- **差异化处理**：景点无位置信息直接移除，餐饮/酒店无位置信息则保留（工具可能不返回坐标）

---

### 9. 请求级日期验证

在 Pydantic 模型层使用 `@model_validator` 实现日期校验，所有使用 `TripPlanRequest` 的路由自动生效：

- `start_date` 必须严格大于今天（最早为明天）
- `start_date` 和 `end_date` 都不能超过未来 4 天（受天气 API 预报范围限制）
- `end_date` 不能早于 `start_date`
- 错误信息包含实际值和期望值，便于用户修正

## 二、项目难点

### 1. LLM 输出的结构化解析与多层容错

**难点描述：**
LLM 的输出是自然语言文本，但系统需要将其解析为严格的 Pydantic 模型。LLM 经常输出不合规的 JSON：
- 在 JSON 前后附加 Markdown 代码块标记（` ```json ... ``` `）
- 字段类型不一致（如 `visit_duration` 返回字符串 `"120分钟"` 而非整数 `120`）
- 嵌套对象格式不一致（如 `location` 有时返回字符串 `"116.4,39.9"` 而非对象）

**解决方案——三层容错链：**

**第一层：JSON 提取（`parse_json_response`）**
自动剥离 Markdown 代码块标记，兼容 ` ```json ``` ` 和 ` ``` ``` ` 两种包裹格式，提取纯 JSON 文本后解析。

**第二层：字段级类型转换（`converters.py`）**
`dict_to_attraction`、`dict_to_hotel`、`dict_to_meal` 三个转换函数对每个字段独立 try-catch：
- `visit_duration`：字符串 → int，失败默认 120 分钟
- `rating`：字符串 → float，失败允许为 None
- `estimated_cost`：字符串 → int，失败默认 0
- `location`：检查是否为 dict 再转换，允许为 None

**第三层：节点级降级（`node_plan_daily`）**
每个规划阶段（景点/酒店/餐饮）独立 try-catch，某阶段解析失败不影响其他阶段：
```python
# 景点解析失败 → 空列表，不影响酒店和餐饮规划
except (json.JSONDecodeError, Exception):
    attractions_data = []
```

### 2. 工具调用型 Agent 的可靠性保障

**难点描述：**
酒店和餐饮 Agent 采用 ReAct 模式调用 MCP 工具搜索真实数据，但面临多重挑战：
- LLM 可能不调用工具，直接编造酒店/餐厅信息
- LLM 可能陷入无限工具调用循环
- MCP 工具本身可能调用失败

**解决方案：**

| 问题 | 防护机制 | 代码位置 |
|------|---------|---------|
| 首轮不调用工具 | `tool_choice="any"` 强制首轮必须调用 | `llm.py` |
| 首轮仍未调用 | 追加警告消息强制重试 | `llm.py` |
| 无限循环调用 | 工具调用 ≥ 2 次后注入停止提醒 | `llm.py` |
| 超过最大轮次 | `max_iterations=8` 硬性上限 | `llm.py` |
| MCP 工具失败 | `ToolsManager.call_tool` 捕获异常返回错误消息 | `tools_manager.py` |
| 工具加载失败 | 降级为纯 LLM 调用（不使用工具） | `llm.py` |

---

### 3. 长期记忆的性能与一致性

**难点描述：**
三层记忆架构涉及 Redis 和 Milvus 两个外部存储，需要解决：
- Embedding 模型首次加载耗时（下载 + 初始化）
- HuggingFace 镜像在国内环境的可用性
- 记忆读写失败不应阻断主流程

**解决方案：**

- **延迟初始化**：Embedding 模型和 Milvus 连接延迟到首次使用时初始化，避免启动时阻塞
- **HuggingFace 镜像修复**：同时设置 `os.environ["HF_ENDPOINT"]` 和 patch `huggingface_hub.constants.HF_ENDPOINT`，解决模块级常量缓存问题
- **优雅降级**：记忆加载/存储失败时仅记录日志，返回空上下文，不影响行程规划主流程
- **用户隔离**：Milvus 检索时通过 `filter` 参数确保只返回当前用户的记忆

---

### 4. MCP 缓存的一致性设计

**难点描述：**
MCP 调用结果缓存需要解决：
- 相同参数不同顺序应命中同一缓存
- 缓存的数据应在 parser 之前（原始数据），保证通用性
- 不同类型数据的时效性差异大（天气 vs 景点详情）

**解决方案：**
- 参数 JSON 序列化使用 `sort_keys=True`，确保参数顺序无关
- 缓存写入在 parser 执行之前，缓存命中后重新执行 parser，保证缓存数据的通用性
- 差异化 TTL：天气 1 小时、景点搜索 24 小时、景点详情 72 小时
- 缓存读写失败仅记录警告，自动回退到实际 MCP 调用

---

### 5. 预算控制的 Prompt-程序双轨约束

**难点描述：**
纯 Prompt 约束无法保证 LLM 严格遵守预算上限，纯程序化计算又无法影响 LLM 的推荐选择。

**解决方案——双轨约束：**

1. **Prompt 层**（引导）：将具体金额上限写入 Prompt，引导 LLM 在推荐时考虑价格因素
2. **程序层**（兜底）：`calculate_daily_budget` 基于 LLM 输出的结构化数据累加各项费用，`check_budget_compliance` 检查是否超标并记录告警
3. **交通费用动态估算**：基于景点间实际距离 × 每公里单价计算，设置最低保底值避免估算过低
4. **总预算汇总**：在 `node_assemble_response` 中汇总所有天的预算，超标时设置 `is_over_budget` 标志返回给前端

---

### 6. 工作节点间的数据依赖与状态管理

**难点描述：**
多个工作节点之间存在复杂的数据依赖关系：
- 每日规划 Worker 需要阶段1的搜索结果和天气数据
- 每日规划 Worker 内部需要景点规划、酒店规划、餐饮规划的协同
- Synthesizer 需要所有工作节点的结果
- 记忆节点需要最终响应数据

**解决方案——状态共享与聚合：**
- 使用 `CoordinatorState`（TypedDict）作为全局状态，所有节点通过返回 dict 增量更新状态
- 通过 `operator.add` reducer 自动合并工作节点的 `completed_tasks`，避免复杂的状态管理
- Orchestrator 根据执行进度动态生成任务，通过条件边实现阶段切换
- 每个工作节点的输入输出边界清晰，便于独立测试和调试

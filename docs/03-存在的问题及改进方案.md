# 项目存在的问题及改进方案

## 一、Agent 层面的问题

### 1. LLM 输出质量不稳定，缺乏重试机制

**现状：**
当前系统对 LLM 的输出只做了 JSON 解析容错（`_parse_json_response` + `_dict_to_*` 类型转换），但如果 LLM 返回的内容在语义层面质量很差（如景点描述过于简略、推荐的景点与用户偏好完全不匹配），系统没有检测和重试机制，会直接使用低质量的结果。

**改进方案：**
- 引入 **输出质量评估器**：在 `_dict_to_attraction()` 等转换方法中增加语义级校验，如检查景点描述长度是否大于 20 字、评分是否在合理范围内
- 实现 **自动重试机制**：当输出质量评分低于阈值时，自动重新调用 Agent，最多重试 2 次
- 增加 **Prompt 动态调整**：重试时在 Prompt 中附加上一次输出的问题描述，引导 LLM 改进

---

### 2. 工作节点间缺乏反馈回路

**现状：**
当前的协调器-工作器架构是单向的：Orchestrator → Workers → Synthesizer。如果 Synthesizer 的验证发现大量景点被过滤（如 LLM 推荐的景点大部分不在目标城市），系统只是记录日志并移除，不会通知工作节点重新规划。最终用户可能看到某一天只有 1 个景点甚至没有景点。

**改进方案：**
- 实现 **反馈回路机制**：当 Synthesizer 验证后某天的有效景点少于 2 个时，触发 Orchestrator 重新生成该天的规划任务
- 在重新规划时，将被过滤的景点名称作为"黑名单"传入 Prompt，避免重复推荐
- 设置最大重试次数（如 2 次），避免无限循环

---

### 3. 每日规划 Worker 内部无法调用工具验证数据

**现状：**
`DailyPlanningWorker` 内部的景点规划和餐饮规划是纯规划型（`enable_tool_calling=False`），它们只能基于阶段1搜索到的原始数据和 LLM 自身的知识来规划。这意味着：
- 景点规划无法验证候选景点的营业时间、是否临时关闭
- 餐饮规划完全依赖 LLM 的知识推荐餐厅，数据可能过时

**改进方案：**
- 将餐饮规划改造为工具调用型，使其能通过高德 MCP 搜索真实餐厅数据
- 为景点规划增加可选的工具调用能力，用于验证景点的实时状态

---

### 4. 缺少交通规划 Worker

**现状：**
系统目前没有交通规划功能。预算中的交通费用是通过 `TRANSPORT_COST_PER_DAY` 字典按预算等级硬编码估算的（经济: 50元/天，适中: 100元/天，豪华: 200元/天），与实际景点间的距离和交通方式无关。

**改进方案：**
- 新增 `TransportPlanningWorker`，在阶段2与其他 Worker 并行执行
- 该 Worker 根据当天景点的位置，规划景点间的交通方式（步行/公交/地铁/打车）和预估时间
- 调用高德地图的路线规划 API 获取真实的交通数据
- 将交通信息集成到 `DailyPlan` 模型中，前端展示景点间的交通建议

---

## 二、架构层面的问题

### 5. CoordinatorState 的内存泄漏风险

**现状：**
协调器-工作器架构使用 LangGraph 的 StateGraph 管理状态，但在长时间运行后，如果状态没有及时清理，可能导致内存持续增长。

**改进方案：**
- 在 `plan_trip()` 方法的 `finally` 块中确保清理所有临时状态
- 增加 TTL 机制：为每个请求状态设置过期时间（如 30 分钟），定期清理过期实例
- 考虑使用更高效的状态管理机制，避免内存泄漏

---

### 6. 并行执行缺乏超时和异常隔离

**现状：**
工作节点使用 LangGraph 的 Send API 并行执行，但存在以下问题：
- 超时后工作节点仍在后台运行，占用资源
- 一个工作节点的异常不会影响其他节点，但异常处理逻辑较为简单（直接使用降级文本）
- 没有对 LLM API 调用的并发数做限制，高并发时可能触发 API 限流

**改进方案：**
- 引入 `asyncio` 替代当前的执行方式，使用 `asyncio.wait_for()` 实现真正的超时取消
- 增加 LLM API 调用的并发信号量（`asyncio.Semaphore`），限制同时进行的 API 调用数
- 实现更细粒度的降级策略：景点搜索失败时使用缓存数据，天气查询失败时使用默认天气

---

### 7. 缺少请求级别的进度推送

**现状：**
行程规划是一个耗时较长的操作（通常 30-60 秒）。前端虽然有 `LoadingProgress` 组件展示进度条，但进度是前端模拟的，与后端实际进度不同步。用户无法知道当前规划到了哪个阶段。

**改进方案：**
- 使用 **Server-Sent Events (SSE)** 或 **WebSocket** 实现实时进度推送
- 后端在每个关键节点发送进度事件：阶段1 开始/完成、阶段2 第 N 天开始/完成、阶段3 开始/完成
- 前端根据实际进度事件更新进度条，提升用户体验

---

## 三、数据层面的问题

### 8. Redis 数据持久化的可靠性

**现状：**
用户数据和行程数据全部存储在 Redis 中。Redis 虽然支持 RDB/AOF 持久化，但作为主存储存在以下风险：
- Redis 重启时可能丢失最近的写入数据
- 数据量增长后 Redis 内存压力增大
- 缺乏复杂查询能力（如按日期范围查询行程）

**改进方案：**
- 引入 MySQL/PostgreSQL 作为主存储，Redis 仅作为缓存层
- 行程数据使用关系型数据库存储，支持复杂查询和数据分析
- 实现缓存一致性策略（Cache-Aside Pattern）

---



## 四、可观测性问题

### 10. 缺少工作节点执行的可视化追踪

**现状：**
系统使用结构化日志记录工作节点的执行过程，但日志分散在多个文件中，难以直观地追踪一次完整的行程规划流程。开发者需要手动搜索 `request_id` 来关联日志。

**改进方案：**
- 集成 **OpenTelemetry** 分布式追踪，为每个工作节点的执行创建 Span
- 实现工作节点执行的可视化面板：展示每个节点的输入、输出、耗时、工具调用次数
- 记录 LLM 的 Token 消耗量，用于成本分析和优化

---

## 五、Prompt 工程问题

### 11. Prompt 与代码耦合，缺乏版本管理

**现状：**
所有工作节点的 System Prompt 都硬编码在 `prompts.py` 文件中。修改 Prompt 需要修改代码并重新部署，无法进行 A/B 测试或快速迭代。

**改进方案：**
- 将 Prompt 模板抽取到独立的配置文件（如 YAML/JSON）或数据库中
- 实现 Prompt 版本管理：每个 Prompt 有版本号，支持回滚
- 支持 A/B 测试：同时运行多个版本的 Prompt，比较输出质量
- 增加 Prompt 模板变量，减少重复内容

---
